# 运营规则 v6

## 当前已授权的运行方式

- 运行模式：`chat_preview`。每 10 分钟检查 RSS，每轮最多展示 3 条预览（含部分预览）。自动完成选题、改写、PS、QA、展示，不等待点评再处理下一条，不加整批样本校准的前置步骤。
- 对话训练稿默认语言：`zh-CN`。每条必须展示“原帖原文 → 拟改写稿 → 修改说明”；越南文稿可保存为未来 production draft，但当前对话不把它当作最终练习稿。用户明确切换语言后才改变 `preview_language`。
- 暂不上传或提交 IFXData；训练阶段也不执行重复的后台只读查询或发布dry-run。标签复用本地已有记录，查重使用本地预览/发布账本。用户明确切换实际发布后才启用 Vietnam 后台查重、标签核验和写入。
- 每日河内 24:00 即次日 00:00（UTC+7，`Asia/Ho_Chi_Minh`），报告刚结束的一整天；不是北京时间 24:00，也不是当天开始时报告未发生的数据。
- 当前任务只使用一个 heartbeat（ID：x），整点起每10分钟触发；00:00同一轮优先生成日报，再检查RSS。不能为同一任务另建第二个定时器或擅自用cron绕过。
- 配置见 sources.json。旧账本向后兼容，不删除历史。定时任务必须固定共享目录并保持单一执行者。
- 筛选边界按 filters.json v3：中国政治仅指内部政治；国际政治、中美经贸、外交会晤及访问抵达/迎接礼仪进入候选，中国公司/企业群体的商业动态继续过滤。历史误判记录 filter_reassessment，并写入 feedback_history 供日报引用，不凭规则升级重置终态或计为新预览。

## 每轮与时效

1. `scripts/patrol.py --output-root <当前任务>/outputs` 是常规入口。先在本地查日报日期，需报告时返回 `reports_first`；完成报告后再运行入口。其余轮次只请求一次 RSS，无新 ID、到期未完成项或新故障时立即安静结束。不要为无事可做的轮次加载完整规则、账本、事件库、X、后台或图片工具。
2. 检查/筛除数不占 3 条额度；最多展示 3 条完整/部分预览或完成获准发布的成稿，其余留队列。正常按原帖 ID 从旧到新处理。
3. 突发/即时行情采用 6 小时试行阈值，以 X 原帖时间核实；超过阈值或时间不明进入 `review`，写明是否仍有报道价值。宏观解释、深度分析不机械过期。不因一条过时或图片失败堵住后面的稿件。
4. 暂时错误本轮只重试一次；保存 block_kind:transient 和至少30分钟后的 retry_after。能力、访问或编辑依据缺失时填具体 resume_condition，不设定时重试；按 [preview-state.md](preview-state.md) 有恢复证据才继续。未到期或等待条件变化的项不抢占后续候选。
5. RSS连续失败、无法登录等相同未变化异常不要每轮重复通知；记录供日报汇总，首次故障/恢复/新需用户处理事项才通知。预览有新增成稿就直接显示。
6. 以新帖子ID作为发现信号。已结束项（基线、跳过、预览、发布）的RSS字段变化只更新缓存，不触发X复核。未完成项的变更在该项下一次到期处理时核对；不越过重试冷却。用户点名旧帖复核或实际发布时重新核对精确原帖。
7. X仅提取目标帖区域；加载失败一次重试后记账继续。不得每次读取整页评论、推荐及趋势。新帖去重通过后才开始图片处理；复用已通过QA的同图版本，纯正文改稿不重做图片。

## 模型路由

`patrol.py`、RSS、日报、账本状态机和 Image1 渲染保持脚本执行，不调用高级模型。`action:work` 时按 [model-routing.md](model-routing.md) 在打开并处理每条帖子前选择一次模型：普通纯文字稿和明确过滤项用 `gpt-6-sol` / `medium`；边界分类、事实冲突、复杂引用或长图用 `gpt-6-astra` / `high`。同一帖子选定后由该模型完成原帖核对、过滤、事件去重、改写、图片判断和修改说明，避免按小步骤反复切换。

编排者保持单一、候选保持串行，只有编排者写共享账本。内部执行者不创建新任务或定时器；它读取最小 `task.json`、当前帖子文件和必要的相关事件记录，不加载完整对话历史或完整账本。若 Sol 开始核对后才发现升级条件，最多升级一次，并在起草或图片编辑前停止，将已提取证据写入 `task.json` 供 Astra 继续。

## 事件去重

预览也进入事件库，避免训练期间反复展示同一消息；正式发布数量始终单独记。

每个通过筛选的候选保存：

```json
{
  "event_key":"机构或主体|具体事件|事件日期",
  "key_facts":["核心事实、数字及确认状态，使用稳定措辞"],
  "event_relation":"new",
  "related_status_ids":[],
  "incremental_facts":[]
}
```

先查最近 7 天 `prepared/preview_partial/previewed/submitting/publish_uncertain/published`（以及已展示部分预览后再次受阻的事件） 的事件记录；长期事件也查相同 event_key。不要把不同日期的例行数据发布混为一个事件。标题相似、主体相同、关键词或 event_key 命中仅用于召回，最终做语义比较：

- **duplicate**：同一事实换措辞、相同截图或重复市场反应，没有新信息；记 skipped / EVENT_DUPLICATE 并关联旧 ID。
- **update**：新数据、正式确认、纠错、政策落地或实质进展；明确列 incremental_facts，正文突出新变化，不重复整篇旧稿。
- **new**：新的事件或独立事实。

脚本阻止同事件完全重复的事实集再次进入 prepared，但无法替代语义判断；不要把换同义词当新增事实。`event_relation:update` 必须有非空新增事实；去重针对信息，而不是禁止同一主题。

## 预览结果

按 [preview-state.md](preview-state.md) 分别记录文字核对、媒体完成和实际展示。全部满足才记 previewed；文字已展示但媒体未完成记 preview_partial，并保存事件事实与阻塞分类。不能以单个 preview_verified 标志代替分项验收。旧 previewed 保留历史，不追认新版 QA。

任务和原稿/编辑稿备份保存在共享 posts/<id>/；用户可见文件及展示回执 MD 放当前任务 outputs/。复用标签缓存，不做后台预览查询。媒体完成后复用现成文字，补齐完整展示再写账。previewed 不再自动入队；用户要求改稿记录 feedback_history，不当新帖再计。

用户明确授权某条实际发布时，才允许 previewed -> submitting 并记录 explicit_publish_override:true 和授权内容；部分预览必须先完成媒体和准备，不能直接提交。原有授权不能覆盖当前暂不发布限制。

## 每日运营报告

每天到点运行 `scripts/daily_report.py`，读取共享账本和运行日志（runtime 目录的 runs/*.json），生成刚结束的河内自然日统计。输出放当前任务 outputs/reports/YYYY-MM-DD.md，同时在对话给出摘要和报告链接。

包含检查轮数、成功/失败次数、发现数、完整预览数、部分预览数、历史未按新版验收的预览数、实际发布数、跳过原因分布、事件重复数、待处理项及阻塞原因、当天采用的用户反馈/规则变更。每个预览/发布项关联原帖与本地成稿；实际发布才列 Newsfeed ID。无数据也出简短日报；没有日志就写“未记录”，不能把缺失当零活动。当前训练模式的实际发布数应为 0，不将 previewed 算入。

保存 report_date、生成时间、时区、数据覆盖范围。用日期去重；定时遗漏后补写未报告日期并注明延迟，不把多天合为一天。`patrol.py`按本任务`outputs/reports/delivery-index.json`返回未展示的已结束日期；已有MD/JSON可直接展示，无需重生成。展示后用`--ack-report YYYY-MM-DD`记入索引。延迟报告生成时传`daily_report.py --delayed`。报告本身不触发发帖。
